## Gate B — proposed backend-only approach (requires explicit approval)
1. Freeze the **actual approved** code commit. Use a **separate release checkout** under `~/bcsentinel-release-candidates/` or an isolated worktree. Do not reset or clean the detached current DEV checkout; do not modify landing page or nginx.
2. Build a **new uniquely tagged DEV backend image from the approved checkout**, using `docker build -f backend/Dockerfile --target runtime -t bcsentinel-dev-s3a2:<approved-shortsha> .` in the candidate root. 3. Use `docker compose` only for the **DEV** services with `docker-compose.dev.yml` and `.env.dev`, never prod. Before touching the live DB, validate image imports and migration head against the isolated restored copy, with the *candidate image*, not an older image with bind mounts. Do not automatically start a second server pointed at active DEV.
4. Schedule a short maintenance window and stop writes (BC test scans, operator actions, scheduled jobs). Verify no active scan is lost. Take final fresh backup; use the new candidate's Alembic to migrate **only DEV postgres** 0037→0040, with a DB URL restricted to DEV and explicit current/head checks. The clone-only test does not itself authorize running against active DEV.
5. Switch only the `dhm-dev-backend` service to the proven new image, preserving DEV networking, volumes, configuration and hostname. The current `docker-compose.dev.yml` has a `build:` backend rather than an image pin; plan an isolated Compose override to pin the exact image. Do not run `docker compose up -d --build` indiscriminately.
6. Check `http://127.0.0.1:8001/health/ready`, public DEV HTTPS, logged request/correlation IDs, expected Alembic head, 1/5/5 historical record invariants adjusted for any legitimate new writes, registration and report preflight. Abort and classify errors before any BC app upload.
7. If the new backend fails, freeze writes and **restore matching pre-upgrade DEV DB backup and prior backend image together**, preserving post-backup writes separately (restoring loses data written since backup). Assess changes and coordinate rollback; never blindly run `alembic downgrade` or restore over active DB. The plan does not include an unattended rollback command.
